# Editorial Engine 승인 필요 목록

> `docs/newsjeoul-editorial-engine-architecture.md`(설계서)에서 발생하는 항목 중 `AGENTS.md` 승인 경계에 해당하는 것만 추려서 별도 정리. 이 문서는 실행 목록이 아니라 **승인 판단용 목록**이다 — 여기 있는 어떤 것도 승인 없이 구현하지 않는다.

## 1. DB 스키마 변경 (신규 테이블 5개, 컬럼 2개)

| 대상 | 종류 | 비고 |
|---|---|---|
| `event_type_rules` | 신규 테이블 | Editorial OS 10유형의 FIXED 값 저장. 데이터만 있고 로직은 없어 리스크 낮음 |
| `daily_zeitgeist` | 신규 테이블 | 하루 1행. 리스크 낮음 |
| `editors` | 신규 테이블 | Persona Registry. 초기 몇 명만 넣고 시작 가능, 리스크 낮음 |
| `topics.editorial_status` | 컬럼 추가 | 기존 컬럼 영향 없음(`ADD COLUMN IF NOT EXISTS` 패턴) |
| `topics.editorial_retry_count` | 컬럼 추가 | 동일 |

전부 기존 컬럼을 변경하거나 삭제하지 않는 순수 추가라 마이그레이션 리스크는 낮음. 다만 **개수가 많아 한 번에 승인받는 것을 제안**(Phase 1에서 한 번에).

## 2. 외부 API 신규 사용

| 항목 | 필요 사유 | 상태 |
|---|---|---|
| 영상 소싱 API(예: YouTube Data API) | §9 "영상" 블록 — 현재 자동 수집 인프라 전무 | **미승인, Phase 5로 보류 제안** |
| 차트용 구조화 데이터 소스(실적·판매량 등, 예: 증권 API/공시 API) | §9 "차트" 블록 — 데이터 자체가 없음 | **미승인, Phase 5로 보류 제안** |

두 항목 모두 이번 설계에서 "생략 가능"으로 처리해 Phase 4까지는 아예 착수하지 않는 것을 제안. 승인 여부와 무관하게 어떤 API를 쓸지(무료/유료, rate limit, 약관)부터 별도 조사가 선행돼야 함.

## 3. 비용/실행시간 증가 요소

| 항목 | 증가 내용 | 비고 |
|---|---|---|
| Layer 1(분류+기획) LLM 호출 | 이벤트당 최대 1회(Rule로 후보 1개면 스킵) | 기존 `resolve-topics`류와 비슷한 급 |
| Layer 2a(본문생성) LLM 호출 | 이벤트당 1회, 장문(1000~2300자) 생성이라 기존 요약형 호출보다 토큰 비용 큼 | **가장 큰 신규 비용 요소** |
| Layer 3b(정성 QA) LLM 호출 | 3a 통과분만, 실패 시 재시도로 추가 호출 발생 가능(상한 있음) | 재시도 상한을 얼마로 할지가 비용 상한을 결정 — §12 Phase 3에서 구체 수치 확정 필요 |
| Zeitgeist 배치 | 하루 1회, 기존 "1일 1회" 함수군과 동일 빈도라 증분 미미 | 낮음 |

**핵심 승인 포인트**: Layer 2a의 장문 생성 비용이 기존 파이프라인(요약/매칭 수준의 짧은 호출 위주)과 단위 비용이 다른 종류라는 점 — 실제 이벤트 처리량(하루 몇 건을 이 파이프라인에 태울지)에 따라 총 비용이 크게 갈리므로, Phase 3 착수 전 **일일 처리 대상 건수 상한**을 먼저 정하는 것을 제안(예: 하루 N건만 장문 생성, 나머지는 기존 요약형 유지).

## 4. 기존 시스템과 충돌 가능성

- 없음으로 판단됨 — 신규 테이블/컬럼은 전부 additive, 기존 `topics`/`stories`/`articles` 파이프라인 로직을 변경하지 않고 그 위에 얹는 구조. 다만 `topics.ai_context`(기존 컬럼)를 Editorial Plan 저장 용도로 겸용하는 부분은, 이 컬럼을 다른 목적으로 이미 쓰고 있는 기존 코드가 있는지 Phase 1 착수 시 재확인 필요.

---

승인 시 착수 순서는 아키텍처 문서 §12 Phase 계획을 따름. 이 목록은 구현 시작 신호가 아니라 판단 자료.
