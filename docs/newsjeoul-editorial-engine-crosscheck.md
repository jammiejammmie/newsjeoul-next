# Editorial OS v1 ↔ Architecture v2 대조 검수

> 디자인팀 `뉴스저울 - Editorial OS v1 설계서.dc.html`과 개발팀 `docs/newsjeoul-editorial-engine-architecture.md`(v2)를 항목별로 대조. **최종 승인 전 상태 — 이 문서 자체는 결정하지 않는다.** "논의 필요" 항목은 채과장 판단 필요.

## 범례
- **유지**: Editorial OS 원안 의도를 그대로 구현하거나, 구현 형태만 채운 것(가치 판단 개입 없음)
- **수정**: 원안에서 명시적으로 값/구조를 바꾼 것이지만 결과물에 미치는 영향이 작아 이견 낮을 것으로 판단
- **논의 필요**: 제품 방향·사용자 경험에 실질적 영향을 주거나, 원안 의도를 개발팀이 해석해 바꾼 지점

## B. 유지 (원안 의도 그대로 구현 형태만 채움)

| 항목 | 구분 | 비고 |
|---|---|---|
| `event_type_rules` 테이블(FIXED 값 룩업화) | 개발팀 구현 형태 제안 | Editorial OS의 유형별 FIXED 값을 그대로 데이터화. 값 자체는 안 바꿈 |
| Rule+AI Hybrid 사건유형 분류 | 개발팀 신규 제안 | Editorial OS는 "판별 신호"만 정의, 판단 알고리즘은 미정의 — 빈 자리를 채운 것. 원안과 충돌 없음 |
| 유형9(분쟁)·10(재난) 안전 오버라이드(AI 판단보다 규칙 우선) | 개발팀 추가 Layer | 원안의 "예외 없음" 문구를 실제로 지키기 위한 구현 강화, 원안 의도를 약화시키지 않고 오히려 보강 |
| 장문 에디토리얼 구조화 출력 스키마(blocks/perspective_markers) | 개발팀 추가(원안엔 출력 형태 정의 자체가 없었음) | QA·프론트 렌더링에 필수적인 빈 자리를 채움. 값·내용에 개입 안 함 |
| QA를 3a(결정론적)+3b(LLM정성) 2단 분리 | 개발팀 구현 형태 제안 | 원안의 "품질검증" 한 스텝을 비용 효율 위해 쪼갠 것, 검증 항목 자체(저품질 패턴 목록 등)는 원안 그대로 가져다 씀 |
| Layer 2a(본문생성) ‖ Layer 2b(근거수집) 병렬화 | 개발팀 구조 변경 | 원안 다이어그램은 순차(생성→미디어배치)지만, 결과물·사용자 경험엔 영향 없는 순수 성능 개선 |
| `type_confidence<0.7` 재분류 루프를 흐름으로 명시 | 개발팀 구체화 | 원안 JSON 주석엔 있었지만 어디서 도는지 안 그려져 있던 것을 흐름으로 그림 |
| Phase 1~5 구현 계획 | 개발팀 신규 추가 | 원안과 충돌 없는 순수 실행 로드맵 |

## C. 논의 필요 (제품 판단 필요)

### 1. 문체(Editorial Style)를 "사건별 AI 판단"에서 "도메인 단위 FIXED"로 격하 — ⚠️ 원안과 다를 수 있음
- **원안**: 파이프라인 다이어그램에 "문체 적용"이 관점 배정 다음의 독립 스텝으로 그려져 있고, 유형별 필드표엔 명시적으로 없지만 JSON 예시엔 `editor_style_profile: "친근한 거래처 직원체"`가 등장.
- **개발팀 해석**: 이 값이 사건마다 바뀌는 값이 아니라 브랜드 전체에 거의 고정된 값으로 보여, 매 사건 AI가 새로 판단하게 하면 오히려 톤이 흔들릴 위험이 있다고 보고 도메인 단위 FIXED로 제안함.
- **왜 논의가 필요한가**: 디자인팀이 "문체 적용"을 독립 스텝으로 그린 데에 실제로 "사건 성격에 따라 미묘하게 톤이 달라지길 원한다"는 의도가 있었을 수 있음 — 이 경우 개발팀 해석은 원안 의도를 축소시키는 것.
- **결정할 것**: 문체가 (a) 도메인당 1개 고정, (b) 도메인+유형 조합마다 다름, (c) 사건마다 AI가 매번 판단 중 어느 쪽에 가까운지.

### 2. Persona Registry("100명 에디터"를 이름·아바타 있는 실제 인격으로 구현) — ⚠️ 원안에 없던 개념
- **원안**: "관점(Perspective)"은 `["엔지니어","소비자전문"]`처럼 추상 라벨로만 존재. 누가 그 관점으로 "말하는" 것처럼 보일지는 정의돼 있지 않음.
- **개발팀 제안**: 이미 프론트엔드에 놀고 있는 `EditorPersona`(이름/아바타/문체) 슬롯을 근거로, 관점을 실제 이름 있는 에디터로 resolve하는 별도 레지스트리(`editors` 테이블)를 신설 제안.
- **왜 논의가 필요한가**: "100명의 디지털 에디터"라는 표현이 (a) 실제로 이름·프로필이 있는 캐릭터를 의미하는지, (b) 단순히 "100가지 분석 관점"이라는 은유적 표현인지가 이번 대화에서 명확히 확인된 적이 없음. (a)라면 이 레이어는 필수, (b)라면 완전히 불필요한 과설계.
- **결정할 것**: 100명 에디터가 바이라인·아바타를 가진 실제 캐릭터인지 여부. 아니라면 Persona Registry 전체를 설계에서 제외.

### 3. 영상·차트 블록을 Phase 5로 보류 — ⚠️ 원안의 필수/강력권장 등급과 충돌
- **원안**: 유형1(신제품)은 "영상(있으면 강력 권장)", 유형7(실적)은 "스파크라인 차트(필수)"로 명시. Research Board·편집 경험 목업도 차트·영상 비중이 시각적 핵심.
- **개발팀 판단**: 현재 코드베이스에 영상 자동 수집(YouTube API 등)·차트용 구조화 데이터 소스가 전혀 없어, 이 두 블록은 "렌더링 문제가 아니라 데이터 조달 자체가 없는 문제"로 보고 초기 Phase에서 제외 제안.
- **왜 논의가 필요한가**: 디자인팀이 이 두 블록을 "있으면 좋은 것"이 아니라 "그 유형 콘텐츠의 정체성"으로 여겼을 가능성(특히 유형7은 "필수"로 명시) — 이걸 미루면 초반 발행물이 목업이 보여준 밀도·개성에 크게 못 미칠 수 있음.
- **결정할 것**: 영상·차트 없이 이미지·텍스트만으로 시작하는 축소판을 1차로 승인할지, 아니면 이 두 블록의 데이터 소스 조사·API 선정을 먼저 진행해 Phase 3에 포함시킬지.

### 4. 재시도 상한 초과 시 "사람 검토 큐" 도입 — ⚠️ "사람 없는 편집국" 비전과 상충 가능
- **원안/기존 비전**: `docs/newsjeoul-ai-editorial-bible.md`의 원래 비전이 "사람 편집국 없이 AI가 담당"임.
- **개발팀 제안**: 재시도 상한(예: 2회) 초과 시 자동 발행하지 않고 사람이 검토하는 큐로 이관.
- **왜 논의가 필요한가**: 안전장치로 넣었지만, "사람 개입 지점을 아예 두지 않는다"는 게 오히려 원래 비전에 더 가까울 수 있음. 사람 검토 큐 대신 "실패하면 그냥 폐기하고 다음 배치에서 처음부터 재시도"만으로 충분할 수도 있음.
- **결정할 것**: 사람 검토 큐를 둘지, 둔다면 누가 그 화면을 실제로 볼 것으로 기대하는지(`/admin`에 새 탭을 만드는 게 맞는 방향인지).

---

## D. 요약 — 승인 판단이 필요한 4가지만

1. 문체를 도메인 FIXED로 둘지, 사건별 AI 판단으로 남길지
2. "100명 에디터"가 실제 인격(이름/아바타)인지, 추상 관점 라벨일 뿐인지
3. 영상·차트를 Phase 5로 미룰지, 먼저 데이터 소스를 조사해 앞당길지
4. 실패 시 사람 검토 큐를 둘지, 완전 무인 재시도로 갈지

나머지(B 항목 전체)는 원안과 충돌 없이 구현 형태만 채운 것이라 별도 승인 없이 확정으로 간주해도 무방하다고 판단됩니다.
