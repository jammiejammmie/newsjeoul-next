# Editorial OS v1 ↔ Architecture v3 대조 검수

> 디자인팀 `뉴스저울 - Editorial OS v1 설계서.dc.html`과 개발팀 `docs/newsjeoul-editorial-engine-architecture.md`를 항목별로 대조. C의 4가지 논의사항은 2026-07-11 채과장 결정으로 **전부 해소되어 A로 이동**, Architecture v3에 반영 완료. 앞으로 새로운 논의사항이 생기면 이 문서에 C로 계속 추가.

## 범례
- **유지**: Editorial OS 원안 의도를 그대로 구현하거나, 구현 형태만 채운 것(가치 판단 개입 없음)
- **수정**: 원안에서 명시적으로 값/구조를 바꾼 것이지만 결과물에 미치는 영향이 작아 이견 낮을 것으로 판단
- **논의 필요**: 제품 방향·사용자 경험에 실질적 영향을 주거나, 원안 의도를 개발팀이 해석해 바꾼 지점

## A. 이미 승인된 것 (참고용, 재논의 대상 아님)

| 항목 | 결정 내용 | 근거 |
|---|---|---|
| 오늘의 화두 공유 배치 자산화 | 이벤트별 반복 추출 → 하루 1회 배치(§5) | "판단이 좋아 보인다"고 명시적으로 확인(2026-07-11) |
| 1. 문체(Style) | **독립 레이어로 유지.** 도메인 고정값 아님 — 사건유형+관점(Persona)의 영향을 받는 가변 레이어로 재설계(Architecture v3 §6) | "신차발표/리콜/실적발표/CEO인터뷰는 분위기·리듬이 다르다"는 이유로 개발팀의 도메인-FIXED 격하안을 기각(2026-07-11) |
| 2. 100명 에디터(Persona) | **Persona Registry 채택.** 단 Persona = 관점+문체+리듬+강조방식을 묶은 Editorial Persona(§7). 구체 인물 설계는 별도 진행 | "100가지 문체가 아니라 100명의 디지털 에디터가 존재하는 편집국"이 목표임을 명확화(2026-07-11) |
| 3. 영상·차트 | **Phase 5 보류 동의.** 단 Block 구조를 처음부터 확장 가능하게 설계(§8 blocks[].type enum 예약) | "Editorial Engine과 장문 콘텐츠 품질이 우선"이나 "목업과의 간극이 커지지 않게" 확장성 전제 조건 부여(2026-07-11) |
| 4. 사람 검토 큐 | **기본 전제로 두지 않음.** Self-Review/QA/Retry/Confidence로 무인 동작, 실패 시 기존 짧은 형태로 자동 강등(§10). 사람 개입은 조회용 Hook만 | "AI 중심 편집국"이 목표, 사람 검토를 기본 흐름에 넣지 않기로 확정(2026-07-11) |

## B. 유지 (원안 의도 그대로 구현 형태만 채움)

| 항목 | 구분 | 비고 |
|---|---|---|
| `event_type_rules` 테이블(FIXED 값 룩업화) | 개발팀 구현 형태 제안 | Editorial OS의 유형별 FIXED 값을 그대로 데이터화. 값 자체는 안 바꿈 |
| Rule+AI Hybrid 사건유형 분류 | 개발팀 신규 제안 | Editorial OS는 "판별 신호"만 정의, 판단 알고리즘은 미정의 — 빈 자리를 채운 것. 원안과 충돌 없음 |
| 유형9(분쟁)·10(재난) 안전 오버라이드(AI 판단보다 규칙 우선) | 개발팀 추가 Layer | 원안의 "예외 없음" 문구를 실제로 지키기 위한 구현 강화, 원안 의도를 약화시키지 않고 오히려 보강 |
| 장문 에디토리얼 구조화 출력 스키마(blocks/perspective_markers) | 개발팀 추가(원안엔 출력 형태 정의 자체가 없었음) | QA·프론트 렌더링에 필수적인 빈 자리를 채움. 값·내용에 개입 안 함 |
| QA를 3a(결정론적)+3b(LLM정성) 2단 분리 | 개발팀 구현 형태 제안 | 원안의 "품질검증" 한 스텝을 비용 효율 위해 쪼갠 것, 검증 항목 자체(저품질 패턴 목록 등)는 원안 그대로 가져다 씀 |
| Layer 2a(본문생성) ‖ Layer 2b(근거수집) 병렬화 | 개발팀 구조 변경 | 원안 다이어그램은 순차(생성→미디어배치)지만, 결과물·사용자 경험엔 영향 없는 순수 성능 개선 |
| `type_confidence<0.7` 재분류 루프를 흐름으로 명시 | 개발팀 구체화 | 원안 JSON 주석엔 있었지만 어디서 도는지 안 그려져 있던 것을 흐름으로 그림 |
| Phase 1~5 구현 계획 | 개발팀 신규 추가 | 원안과 충돌 없는 순수 실행 로드맵 |

## C. 논의 필요 (현재 없음)

2026-07-11 시점 논의사항 4개 전부 A로 이동해 해소됨. 새로운 논의사항이 생기면 여기에 같은 형식(원안/개발팀 제안/왜 논의가 필요한가/결정할 것)으로 추가.

## D. 요약
