# 1. SEO 전략

### AI 검색 시대 SEO
AI 검색(ChatGPT, Perplexity, Gemini)은 답을 대신 주고 트래픽을 안 준다는 근본적 긴장이 있다(Red Team 2번). 그래도 초기 단계에선 **인용을 통한 인지도 확보가 트래픽보다 우선**이다 — 아무도 모르는 서비스는 인용조차 안 된다.
- AI 크롤러(GPTBot, PerplexityBot, Google-Extended, ClaudeBot)는 초기엔 **허용**한다. 트래픽 규모가 커지면 그때 재검토한다(지금 차단하면 인지도 확보 기회 자체가 없다).
- `llms.txt`를 신설해 AI 에이전트에게 사이트 구조(Node/Story/Timeline 구분)를 명시적으로 안내한다.
- Node의 **summary(인용용 문장)**는 Product Bible 5장 원칙대로 1~2문장, 주어·수치·날짜를 명시한 자기완결형으로 작성 — 이게 AI가 그대로 인용하기 좋은 형태다.
- 루머/확정 구분(Product Bible 0장 원칙)을 `ClaimReview` 구조화 데이터로 표기하는 것을 검토한다 — 이건 AI 검색 신뢰도 신호로도, Google 팩트체크 리치 리절트로도 작동할 수 있는 일석이조 장치다.

### Google 검색
- Core Web Vitals, E-E-A-T(경험·전문성·권위·신뢰) 신호 — Organization schema로 발행 주체를 명확히 한다.
- Topic 페이지의 "지금" 섹션은 **자기완결형 요약**으로 구성해 Featured Snippet을 노린다 — 이건 탐험 유도용 explanation과 반대 성격이므로 섹션을 명확히 분리한다(이미 결정된 원칙 재적용).
- Node 라우트를 사이트맵 최우선순위로.

### Bing
- Bing 자체 검색 점유율은 낮지만 Bing Copilot(AI 검색)의 인덱스 기반이다. Google과 동일한 기술적 SEO(사이트맵, 구조화 데이터)로 무료로 커버되므로 별도 투자 없이 Bing Webmaster Tools에 사이트맵만 제출한다 — 낮은 우선순위, 제로 비용 항목.

### Naver
- 한국 뉴스 검색 점유율 1위 — 장기적으로 가장 중요한 채널이지만 **뉴스 검색 제휴는 사업개발 영역**이라 Phase 4로 미룬다(기존 결정 유지).
- 지금 할 수 있는 것: Naver 크롤러(Yeti) 기준 기술적 SEO, Topic의 "지금" 섹션을 **Naver 지식스니펫** 형태(질문-답 구조)로도 최적화 — 제휴 없이도 가능한 부분.

### 구조화 데이터 (체크리스트)
`Organization`, `WebSite`(sitelinks 검색창), `NewsArticle`(Story), `Article`+`FAQPage`(Topic), `Event`(Timeline), `BreadcrumbList`(전 페이지), `ClaimReview`(루머/확정 라벨, 신규 검토).

### Topic SEO
- 키워드 타겟: "OO 총정리", "OO 정리", "OO 지금까지". Title 패턴: `{name} 총정리 — 지금까지 정리 | 뉴스저울`.
- `updated_at`을 화면에 노출해 최신성 신호로 활용.
- canonical은 slug 기준 고정, 절대 변경하지 않는다(User Journey의 "북마크" 신뢰와도 직결).

### Story SEO
- `NewsArticle` schema 유지. Google News Publisher Center 등록 여부는 기존 사이트 기준으로 별도 확인 필요(이 문서 범위 밖 — 구현 단계에서 점검 항목으로 남긴다).
- Story는 SEO 자산으로서는 단명하므로, 유입된 트래픽을 Node로 넘기는 배너(Implementation Bible Step 5)가 SEO 전략의 실질적 핵심이다.

### Timeline SEO
- `Event` schema. Timeline은 시간이 지나도 삭제되지 않고 계속 길어지는 **에버그린 자산**이라는 게 SEO적으로도 핵심 — Product Bible 3장 "시간이 지날수록 두꺼워지는 페이지" 철학의 검색엔진 버전.

# 2. 바이럴 전략

### 채널별 전략
- **Threads**: 기존 파이프라인을 Story 중심에서 Node 중심으로 전환(로드맵 기존 항목), 카피 로테이션(A~E) 유지, **침묵지수를 다시 핵심 트리거로 전면 배치**(Amendment Plan 반영).
- **X**: Timeline 데이터를 그대로 활용한 스레드(연속 트윗) 포맷 — "이 이슈가 어떻게 흘러왔는지"를 자동 생성 가능. X의 인용/반박 문화는 "같은 사건, 다른 헤드라인" 컨셉과 정합성이 높다.
- **Reddit**: 국내 트래픽 채널로는 지금 우선순위 낮음. 국제화(Phase 5)와 연결되는 지점으로만 관찰.
- **Facebook**: 한국 내 뉴스 공유 채널로서는 감소 추세 — 낮은 우선순위. 다만 시니어층 리텐션이 필요해지면 재검토.
- **LinkedIn**: 기업/산업 Entity 콘텐츠(반도체, 시장 분석 등)가 이 채널 소비층과 정합 — B2B 수익 전략(4장)의 신뢰 구축 채널로 포지셔닝, 바이럴보다 전문성 노출 목적.

### 공유 심리 → 실행 전략
- 공유 트리거 시점은 User Journey에서 이미 식별됨(10분 구간, 첫 "놀라움" 발견 직후) — 이 시점에 공유 버튼이 눈에 띄어야 한다.
- **침묵지수를 활용한 공유 구조**: "20개 언론사 중 2개만 보도" 같은 숫자 카피를 공유 텍스트에 자동 삽입(기존 Threads 템플릿 방식을 Node 링크로 확장). 숫자로 검증된 놀라움은 이 서비스의 가장 강력한 바이럴 원자재다 — Red Team 5번 지적대로 절대 부차화하지 않는다.
- **자발적으로 퍼가는 요소**: (a) Timeline을 이미지 카드로 자동 렌더링해 캡처·공유하기 쉽게 만든다(Phase 2 후보). (b) "예상외 연결" 발견 시 자동 캡션 생성 — 예: "몰랐던 연결: 아이폰17은 사실 이렇게 관세 이슈와 이어져 있다."

# 3. 리텐션 전략

- **D1**: "오늘 새로 바뀐 것" 피드가 어제 본 대상을 우선 노출 — 재방문 이유를 구조적으로 제공.
- **D7**: 습관 형성 초기 — 알림 없이도 자발적 재방문이 일어나는지가 진짜 제품-시장 적합성의 신호(가장 정직한 검증 지표).
- **D30**: 진짜 승부처(User Journey에 이미 명시) — 이 시점부터 팔로우 수요가 실질적으로 발생.
- **저장(Phase 1 저비용 제안, 신규)**: 로그인 없이 로컬스토리지 기반 "최근 본 대상" 목록 — 계정 시스템 없이도 구현 가능한 최소 리텐션 장치. Phase 1에 낮은 비용으로 추가할 가치가 있다.
- **팔로우/알림 — 중요한 공백 인정**: 팔로우와 알림은 전부 **계정 시스템**을 전제로 한다. 그런데 지금까지 어떤 문서에도 로그인/계정 설계가 없다. 이건 이번 Growth Bible에서 처음 드러난 공백이다 — **계정 시스템 도입은 Phase 3(팔로우 기능) 착수 직전에 반드시 선행**되어야 하는 항목으로 로드맵에 명시한다.
- **습관 형성 원칙**: 정해진 시간 알림(예: "매일 아침 9시")보다 Product Bible 2장의 간헐적 강화 원리를 그대로 적용 — 예측 불가능한 타이밍에 터지는 "놀라움"이 고정 알림보다 습관 형성에 효과적이라는 전략을 채택한다.

# 4. 수익 전략

### 도구별 평가와 도입 순서
계정 시스템이 없어도 되는 것부터, 있어야 하는 것 순으로, 데이터 자산이 쌓여야 가능한 것을 마지막에 둔다.

1. **Newsletter (Phase 2 초입)** — 이메일 주소만으로 시작 가능한 가장 가벼운 단계. 아직 유료화 아님, 이후 Premium의 구독자 씨앗이 된다.
2. **Adsense (Phase 2)** — 트래픽이 일정 규모 이상일 때, Product Bible 8장(광고 위치/분리 원칙) 그대로 적용.
3. **Affiliate (Phase 2~3)** — `product` 타입 Entity(아이폰17, 갤럭시 등)와 자연스럽게 연결되는 구매 링크. 반드시 "제휴 링크" 라벨링, 콘텐츠와 시각적으로 분리(Product Bible 0장 원칙 그대로).
4. **Sponsorship/브랜드 광고 (Phase 3)** — 맥락이 맞는 Topic/Entity에만, "협찬" 라벨 필수(기존 결정 유지).
5. **Premium 구독 (Phase 3)** — 계정 시스템이 이미 전제된 시점(팔로우/알림과 함께 도입하는 게 자연스럽다). 후보 기능: 무제한 팔로우, 알림, 광고 제거, 주간 프리미엄 리포트.
6. **B2B API / Data Licensing (Phase 4)** — 지식그래프(Topic-Entity-Relation) 데이터가 충분히 쌓인 뒤, 투자사·리서치사·미디어사 대상. Red Team 7·10번 지적(가장 아쉬운 공백, 최우선 투자 대상)에 대한 정면 응답.
7. **Enterprise (Phase 5)** — B2B API의 상위 개념(커스텀 SLA, 전용 대시보드). 데이터 자산과 신뢰가 충분히 축적된 뒤에만 의미가 있다.

**원칙**: 계정 불필요 → 계정 필요 → 데이터 자산 필요 순으로 도입한다. 이 순서를 거꾸로 가면(예: 데이터도 없는데 B2B API부터) 팔 것이 없는 상태에서 영업만 하게 된다.

# 6. 10년 로드맵

- **1년**: Phase 1~2 완료. Node 기반 탐험 구조 정착, 실사용자 데이터로 핵심 가정(탐험 깊이, 재방문) 검증. 계정 시스템 없음, 수익은 뉴스레터/Adsense 초입 단계. "한국에서 유일한 이슈 탐험 플랫폼"으로 인지도 시작.
- **3년**: Phase 3 완료. 계정·팔로우·알림, 그래프 시각화, Premium 구독 첫 출시, B2B 데이터 판매 파일럿 시작. 목표는 "뉴스 안 보는 사람도 아는 서비스" — 뉴스 카테고리를 벗어난 브랜드 인지도.
- **5년**: Phase 4~5 일부. 네이버 제휴 완료, 최소 영어 버전으로 국제화 시작, B2B 데이터 라이선싱이 유의미한 매출 라인으로 성장. 한국 이슈 지식그래프의 사실상 표준 참조 소스 중 하나로 자리잡음.
- **10년**: "뉴스 사이트"가 아니라 "세상의 이슈와 관계를 구조화하는 데이터 기업"으로 인식됨. 국내에서 시작한 지식그래프가 다른 언어권으로 확장되어 있을 가능성. 이 시점에 "뉴스저울"이라는 이름 자체가 브랜드 리뉴얼 후보가 될 수 있다 — Product Bible 0장 원칙 6("이름을 떼도 성립해야 한다")이 실제로 실현되는 시점.

# 7. 자동화 원칙 (Autonomy-First)

뉴스저울은 "서비스"가 아니라 "자동으로 성장하는 시스템"이다. 뉴스 사이트도, 뉴스 공장도 아니다 — 자동으로 배우고, 자동으로 생성하고, 자동으로 검증하고, 자동으로 배포하고, 자동으로 성장하는 시스템이다.

**핵심 테스트**: 모든 기능/설계는 "이 기능은 사람이 매일 관리해야 하는가?"를 통과해야 한다. YES면 재설계한다 — AI 또는 시스템이 대신하도록 구조를 바꾼다.

**최종 KPI 재정의**: 트래픽이 아니라 **사람이 하루 동안 개입한 시간**이다. 목표는 하루 평균 5분 미만. (Product Bible의 "세션당 탐험 깊이/재방문율"은 제품 성공 지표로 계속 유지한다 — 이 KPI는 그와 별개로, 운영 자동화 성숙도를 재는 지표다. 둘 다 동시에 추적한다.) 관리자는 운영자가 아니라 예외만 처리하는 감독관이다.

### 자동화 성숙도 로드맵 — 기능 로드맵(6장)과 별개의 축
기능 로드맵이 "무엇을 만드는가"라면, 이 축은 "그것을 누가 계속 돌보는가"다. 같은 Phase 번호를 쓰지만 서로 다른 두 축이 동시에 진행된다.

| Phase | 자동화 대상 |
|---|---|
| Phase 1 | 자동 수집, 자동 분류, 자동 생성, 자동 게시 |
| Phase 2 | 자동 품질 평가, 자동 수정, 자동 SEO, 자동 SNS 배포 |
| Phase 3 | 자동 학습, 자동 A/B 테스트, 자동 랭킹 최적화, 자동 내부링크 최적화 |
| Phase 4 | 자동 수익 최적화, 자동 광고 위치 최적화, 자동 추천 최적화, 자동 개인화 |
| Phase 5 | 사람 없이도 365일 계속 성장하는 시스템 |

### 향후 모든 기능 설계에 필수 — 3문항 기록
새 기능을 설계할 때마다 반드시 기록한다: **① 무엇이 자동인가 ② 무엇이 아직 사람을 필요로 하는가 ③ 사람이 하는 일을 AI가 대신하려면 무엇이 더 필요한가.** 이 3문항은 Implementation Bible의 각 Step에도 소급 적용해야 한다 — 다음 v0.2 갱신 때 반영한다.

### 기존 설계에 미치는 영향 (즉시 짚어야 할 것)
- **관리자 수동 Topic 생성 폼**(Amendment Plan에서 이미 Phase 2로 후순위 조정됨): 이 원칙 하에서 "정기 워크플로"가 아니라 "AI가 못 찾은 이슈의 씨앗만 사람이 심는 예외 도구"로 재정의한다 — 매일 쓰는 도구면 그 자체로 설계 실패다.
- **품질 채점 후 저신뢰 항목 큐잉**(Implementation Bible Step 2.5, 신규): "매일 검토"가 아니라 "임계값 이하만, 배치로 몰아서, 검토는 선택사항"으로 설계한다. 관리자가 매일 큐를 확인하는 습관 자체가 이 원칙 위반이다 — 저신뢰 항목은 기본적으로 비공개로 안전하게 묻히고, 방치돼도 서비스가 죽지 않아야 한다.
- **1일 1회 배치(Relationship 생성 등, Phase 2)**: 이미 사람 개입 없는 자동 스케줄이라 원칙에 부합 — 그대로 유지.

# 8. Data Never Dies / Evergreen Data 원칙

뉴스저울은 뉴스를 소비하는 서비스가 아니라, 시간이 지날수록 가치가 커지는 데이터 자산을 구축하는 프로젝트다. 뉴스는 소비되고 사라지는 콘텐츠가 아니라 미래를 위한 데이터 포인트다.

오늘은 오래된 기사라도 내일은 "역사"가 되고, 5년 뒤엔 "연구 자료"가 되고, 10년 뒤엔 "시대를 보여주는 증거"가 된다. 예: 2026년 GPT-6 기사 → 2028년 GPT-7 기사 → 2032년 "GPT는 어떻게 발전했는가?"라는 검색이 들어오면 2026년 기사는 새로운 가치로 다시 살아난다. 기사는 죽지 않는다 — 맥락이 바뀌며 계속 살아난다. (1장 Timeline SEO의 "에버그린 자산" 서술과 같은 원리다.)

뉴스저울의 자산은 '기사 수'가 아니라 **'시간과 함께 축적되는 데이터'**다. 모든 Topic은 시간이 흐를수록 더 두꺼워지고, Timeline은 계속 길어지며, Relation은 계속 늘어나고, Story는 새로운 의미를 얻는다.

### 구현 원칙
1. 가능한 모든 데이터는 보존한다.
2. 삭제보다 비활성화를 우선한다.
3. 덮어쓰기보다 Version을 남긴다.
4. Timeline은 끝나지 않는다.
5. 과거 데이터도 현재 데이터와 동일하게 검색 가능해야 한다.
6. 오래된 데이터도 현재 Topic과 자동 연결될 수 있어야 한다.
7. AI가 발전할수록 과거 데이터를 다시 분석·재평가할 수 있도록 원본을 최대한 보존한다.

이 원칙은 Autonomy-First(7장)와 함께 뉴스저울의 장기적 핵심 철학으로 유지한다. DB 설계 층위(Append-only/Version-first/History-first)의 구체적 반영은 Implementation Bible Step 0에서 다룬다.

# 9. Living Knowledge (살아있는 지식) — Data Never Dies의 확장

Data Never Dies가 "데이터를 버리지 않는다"라면, Living Knowledge는 "같은 데이터도 AI가 발전할수록 계속 더 똑똑해진다"는 원칙이다. 데이터는 그대로지만 지식은 계속 성장한다.

예: 2026년 GPT-6 기사 → AI v1 분석 → 2028년 AI가 다시 분석 → 새로운 Relation 발견 → 2032년 새로운 Summary 생성 → 2035년 새로운 검색어와 연결 → 2040년 또 다른 관점으로 재분석.

일반 뉴스 사이트는 "기사 작성 → 끝"으로 끝나지만, 뉴스저울은 "기사 저장 → AI 재분석 → 새로운 관계 생성 → 새로운 Timeline 연결 → 새로운 Summary 생성 → 새로운 검색에서 다시 발견"이라는 순환 구조여야 한다. AI가 발전할수록 과거 데이터도 함께 가치가 커져야 한다 — 새 모델(GPT-7, GPT-8, GPT-9...)이 나오면 기존 데이터를 다시 분석하는 것은 특별한 이벤트가 아니라 뉴스저울의 기본 동작이다.

### 향후 모든 설계가 통과해야 하는 4가지 질문
① 이 데이터는 미래 AI가 다시 분석할 수 있는가? ② 새로운 관계를 발견할 수 있는가? ③ 새로운 Summary를 만들 수 있는가? ④ 새로운 검색 의도에서도 다시 발견될 수 있는가?

### 최상위 철학 (Product Bible Vision과 동일)
"뉴스저울은 뉴스를 소비하는 서비스가 아니라, 시간이 흐를수록 AI와 함께 스스로 더 똑똑해지고 가치가 커지는 살아있는 지식 데이터베이스를 만드는 프로젝트다."

이 원칙은 8장(Data Never Dies)이 전제하는 "보존된 원본"이 있어야 성립한다 — 원본을 지우면 재분석할 대상 자체가 사라지므로, 두 원칙은 항상 함께 적용된다.
